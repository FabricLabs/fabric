Application Resource Contracts

Gossip carries the postcard. An ARC is the notebook the postcard is about: who may write, what the tip is, and how Bitcoin spends it.

Gossip is the road. An ARC is the notebook.

      01 · the idea

      The road is not the agreement

      The last walkthrough was gossip: Peers, hallways, signed envelopes, bit-identical flood. That is how bytes move.

      An Application Resource Contract is not a new kind of envelope. It is a published agreement those envelopes refer to — primitives, members, a spend policy, a Bitcoin anchor. Relays can carry the postcards without keeping the notebook.

      02 · the wire

      Same three outer types

      ARC is not a new opcode family. The public flood already has the whole surface:

      1. CONTRACT_PUBLISH (0x5f) — genesis.
      2. CONTRACT_MESSAGE (0x60) — namespaced events. Body must include contract: <id>.
      3. CONTRACT_PROPOSAL (0x8a) — batched messages, Merkle, JSON Patch, optional PSBT.

      Inner type strings (GroupChat, GroupChange, …) live in the body. They are not outer opcodes.

      03 · genesis

      The first page declares the rules

      A 0.1 ARC genesis names four things:

      1. Primitives — which CONTRACT_MESSAGE body types (and optional Machine opcodes) are in-bounds. An empty messageTypes list is deny-all, not fail-open.
      2. Members — who may read, who may sign, and the threshold.
      3. Spend policy — how tip state maps to a Bitcoin P2TR.
      4. Anchor — a Bitcoin block hash (64-hex) binding publish time to L1.

      Unknown extra fields are ignored by core. Invalid spend policy fails closed.

      04 · the name

      First writer wins

      The namespace id is Actor(definition).id after CONTRACT_PUBLISH. That id is the name of the notebook.

      A second signed genesis for the same id is a different envelope. The register keeps the first. That is the same first-writer-wins rule the gossip walkthrough already mentioned — it belongs to the contract, not to the hop.

      05 · the tip

      Clock, digest, Bitcoin tip

      Each ARC keeps a tip: clock, content, and stateDigest = SHA-256 of the canonical { version, clock, content }. It also remembers a bitcoinBlockHash (and preferably height).

      Every accepted transition that advances the clock should refresh that block hash to the peer’s current Bitcoin tip. Withdrawals must cite both the digest and the block hash they claim — not a paraphrase of last week.

      06 · accumulate

      Same bytes, same fold

      Publisher and participants ingest the same signed AMP bytes from the mesh, an opaque hub queue, or a pasted fabric:<hex>. Identity is the AMP body hash. Fold is sorted by hash, so arrival order does not pick the winner.

      That is why gossip must be bit-identical. If a relay rewrote the postcard, honest notebooks would diverge.

      07 · unknown ids

      Carry what you do not keep

      A gossip Peer still floods CONTRACT_MESSAGE for a namespace it has never opened. Applications ignore unknown ids. The road does not have to understand the notebook.

      scripts/gossip-relay.js is that posture in miniature: registerInboundContracts off, validate and carry, no tip state.

      08 · members

      Readers, signers, Tokens

      Genesis sets the first roster. Later, a ContractCapabilityGrant can issue a Token: OP_CONTRACT_READ or OP_CONTRACT_SIGN, bound to this contractId.

      Verifying a Token without the issuer key is not authorization. The result is labeled unverified. Parse and verify are different acts.

      09 · who may mutate

      A valid envelope is not enough

      Ingest must not fold GroupChange (or other member/spend mutations) on AMP signature alone. The author must already be in the current signer set, or present a verified OP_CONTRACT_SIGN Token for this id.

      Anyone can gossip a postcard. Only a signer can turn the page.

      10 · chat under the id

      GroupChat is not the shoutbox

      GroupChat appends under the contract. Policy is reader ∪ signer (or a matching Token). Optional groupChatSeal is wave-1 confidential messaging — relays need not open the seal.

      MessageReceived and MessageReceipt are a sidecar two-phase commit. They do not advance the tip clock. Delivery ACK is not a state transition.

      11 · k-of-n

      Propose, then vote

      GroupChangeProposal names a roster. GroupChangeVote is a BIP-340 vote on that exact bag. Fold uses genesis/tip k-of-n. A proposer threshold cannot lower the bar.

      Federation invites (FederationContractInvite + response) are the join flow. They are still CONTRACT_MESSAGE bodies, still under the same id.

      12 · spend

      Withdrawals bind the tip

      resolveSpend({ genesis, tip }) builds the P2TR from spend policy plus the current signer keys. ContractWithdrawalRequest must bind stateDigest and bitcoinBlockHash (and destination, fee, …) to that tip. Witnesses cite the same fields plus requestId.

      Accumulate refuses a stale binding. You cannot spend last month’s notebook with this month’s coins.

      13 · compute vs vault

      The machine is not the lock

      Machine + Program are deterministic compute and a commitment. Taproot is the spend surface. A program run does not, by itself, change the P2TR address — unless the tree actually includes a hashlock leaf.

      When genesis lists primitives.opcodes, the machine fails closed on anything outside that list.

      14 · Hub and Beacon

      Accept overlays spend

      Hub Accept takes a published genesis into the Beacon contracts root and provisions a namespace sidechain at /namespaces/<id>. Spend address is overlaid at Accept so the Actor id can stay stable across Bitcoin networks. Do not freeze the tip block hash into Beacon genesis if that stability is required.

      fabric-beacon is itself a native ARC. Epoch sealing (BEACON_EPOCH / beacon/CHAIN) stays on the Beacon service — it is not application CONTRACT_MESSAGE traffic.
